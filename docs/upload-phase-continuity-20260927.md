# Upload relationships and phase programme authority

A filename is not programme authority or a reliable replacement instruction. The Schedule upload panel requires a purpose: baseline, progress update, revised baseline, recovery, or scenario; and coverage: whole project or one named phase. Baseline adoption requires an approval reference when its purpose is explicitly confirmed. The reference is recorded evidence of the user's decision, not independent verification of the issuing party's approval. Recovery/scenario uploads remain scenarios. Candidates can have their purpose/reference reviewed before adoption; adopted history cannot be relabelled.

Each phase retains separate schedules, source documents and adopted baseline/current selections. Uploading or adopting a later phase never advances the whole-project Data Date or replaces its current programme. Phase positions persist through gateway restart. Ask phase questions return phase programme positions and their own dates; phase commercial/Delivery metrics and automatic cross-phase consolidation are not inferred. A coordinated whole-project programme is required for the combined programme.

Documents expose a revision-bound relationship decision: new independent record, correction/replacement of a selected active record, or amendment of the selected base contract. The decision records source hashes, target source hash, note and timestamp and rejects stale project versions. An amendment remains a delta; it does not replace the base contract. Multiple revisions with the same business identifier are held for review until a replacement is selected. Exact duplicate bytes are retained once in the active/additive calculation population. Source document identifiers are retained from the parsed content, independently of numeric assertions and filenames. A later VO/amendment without an established source identifier remains a candidate until its relationship is reviewed. A reviewed new independent record can share a filename with an earlier record. Where identifiers or intent are ambiguous, users must review the relationship; filenames do not establish the intended business meaning.

Complete BOQ revisions replace the selected BOQ basis. Same-name and renamed files behave alike. Existing governed quantity/package links carry forward only where item number, section, description and unit match uniquely in both revisions. Changed/ambiguous scope retains unresolved links and findings. Required quantities and values come from the newly adopted BOQ; retained installed measurements keep their original receipts. There is no filename-based merge or inferred VO adjustment to BOQ quantities.

Project versions change on review/adoption; the gateway invalidates that project's read cache and recalculates dependent pages. Other projects retain their own state. Retained Ask analyses/downloads remain immutable; new queries and refreshed live views use the current version.

## Verification

`project-upload-continuity.test.ts` exercises same/different filenames, duplicate bytes, several pending corrections, stale decisions, exact BOQ identity, purpose review, baseline approval references, separate baseline/update/scenario/phase decisions, cross-scope rejection, HTTP routes and durable restart. `project-ask.test.ts` additionally checks BOQ replacement against Delivery and Ask, independent projects and phase-versus-whole-project dates. Browser and final release results are recorded in the release feedback after deployment review.
